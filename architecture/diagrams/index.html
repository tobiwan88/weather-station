    Sensor Data Flow

    Sensor trigger → event → consumers sequence.

    ---
title: Sensor Data Flow (Event-Driven)
---
sequenceDiagram
    participant TMR as fake_sensors_timer<br/>(k_timer ISR)
    participant TRIG as sensor_trigger_chan<br/>(zbus)
    participant FTEMP as fake_temperature<br/>(zbus listener)
    participant FHUM as fake_humidity<br/>(zbus listener)
    participant EVCHAN as sensor_event_chan<br/>(zbus)
    participant GW as gateway listener<br/>(LOG_INF)
    participant DASH as http_dashboard<br/>(ring buffer)
    participant BROWSER as Browser<br/>GET /api/data

    Note over TMR: Every AUTO_PUBLISH_MS
    TMR->>TRIG: pub sensor_trigger_event<br/>{ source=TIMER, target_uid=0 }

    Note over TRIG,FHUM: zbus dispatches to all listeners
    TRIG->>FTEMP: listener callback
    FTEMP->>FTEMP: read milli-°C → Q31 encode
    FTEMP->>EVCHAN: pub env_sensor_data<br/>{ uid, TEMPERATURE, q31, ts }

    TRIG->>FHUM: listener callback
    FHUM->>FHUM: read milli-%RH → Q31 encode
    FHUM->>EVCHAN: pub env_sensor_data<br/>{ uid, HUMIDITY, q31, ts }

    Note over EVCHAN,DASH: zbus dispatches to all subscribers
    EVCHAN->>GW: listener callback → LOG_INF
    EVCHAN->>DASH: listener callback

    Note over DASH: acquire k_spinlock
    DASH->>DASH: append (ts, q31) to ring buffer
    Note over DASH: release k_spinlock

    Note over BROWSER,DASH: Later — HTTP GET /api/data
    BROWSER->>DASH: HTTP GET /api/data
    Note over DASH: acquire k_spinlock
    DASH->>DASH: memcpy snapshot
    Note over DASH: release k_spinlock
    DASH->>DASH: serialize snapshot → JSON<br/>(no lock held)
    DASH-->>BROWSER: 200 OK { sensors: [...] }

    participant LOC as location_registry<br/>priority 96

        HTTP->>CC: publish CONFIG_CMD_SET_TRIGGER_INTERVAL

        CC-->>SNTP: zbus listener callback
        SNTP->>SNTP: k_work_reschedule(&immediate_work, K_NO_WAIT)
        Note over SNTP: Runs async in work queue<br/>performs SNTP query
    end

    alt sensor_<uid>_name present and USER_META enabled
        HTTP->>SR: sensor_registry_set_meta(uid, .display_name="Kitchen")
        alt SETTINGS enabled
            SR->>SR: settings_save_subtree(...)
        end
    end

    alt action=add_location / action=remove_location
        HTTP->>LOC: location_registry_add/remove(name)
        alt SETTINGS enabled
            LOC->>LOC: settings_save_subtree(...)
        end
    end

    alt mqtt_* fields present
        HTTP->>CC: publish CONFIG_CMD_MQTT_SET_*
        CC-->>MQTTP: zbus listener callback
        MQTTP->>MQTTP: update config, reconnect if needed
    end

    HTTP-->>BR: 303 See Other → /config

    Concurrency — Snapshot Pattern

    How the HTTP dashboard safely shares ring buffer data between an ISR-derived producer and an HTTP handler thread without holding the lock during serialisation.

    ---
title: Concurrency — Snapshot Pattern
---
sequenceDiagram
    participant ISR as fake_sensors_timer<br/>(k_timer ISR)
    participant TRIG as sensor_trigger_chan<br/>(zbus)
    participant SENSOR as fake_temperature<br/>(zbus listener)
    participant EVCHAN as sensor_event_chan<br/>(zbus)
    participant DASH_L as http_dashboard<br/>listener (ISR-derived)
    participant RING as ring_buffer<br/>(shared state)
    participant DASH_H as http_dashboard<br/>HTTP handler thread
    participant BR as Browser

    Note over ISR: k_timer fires (ISR context)
    ISR->>TRIG: pub sensor_trigger_event K_NO_WAIT
    TRIG->>SENSOR: listener callback (zbus thread)
    SENSOR->>EVCHAN: pub env_sensor_data K_NO_WAIT
    EVCHAN->>DASH_L: listener callback (ISR-derived)
    Note over DASH_L: k_spinlock_lock (ISR-safe)
    DASH_L->>RING: append (ts, q31)
    Note over DASH_L: k_spinlock_unlock
    DASH_L-->>EVCHAN: return immediately

    Note over BR,DASH_H: Later — HTTP GET /api/data
    BR->>DASH_H: GET /api/data
    Note over DASH_H: k_spinlock_lock
    DASH_H->>RING: memcpy → local snapshot
    Note over DASH_H: k_spinlock_unlock
    Note over DASH_H: serialize snapshot → JSON<br/>(no lock held — O(n) safe)
    DASH_H-->>BR: 200 OK { sensors: [...] }

sequenceDiagram

    participant HTTP as HTTP dashboard<br/>/api/fota/*
    participant FLASH as flash_img<br/>(slot 1)
    participant BOOT as MCUboot
    participant APP as Zephyr app<br/>(new image)
    participant CONF as fota_confirm<br/>SYS_INIT 99

    DEV->>HTTP: POST /api/fota/upload<br/>(zephyr.signed.bin, octet-stream)
    Note over HTTP: flash_img_init(slot1)<br/>stream chunks via<br/>flash_img_buffered_write()
    HTTP->>FLASH: write image progressively
    HTTP-->>DEV: 200 OK { sha256: "..." }

    DEV->>HTTP: POST /api/fota/apply
    HTTP->>BOOT: boot_request_upgrade(TEST)
    Note over HTTP: k_work_schedule reboot +2 s
    HTTP-->>DEV: 200 OK
    Note over HTTP: reboot

    Note over BOOT: Verify ED25519 signature
    Note over BOOT: SWAP_MOVE slot1 → slot0
    BOOT->>APP: boot new image

    Note over APP: All SYS_INIT libraries init
    APP->>CONF: SYS_INIT APPLICATION 99
    Note over CONF: k_work_schedule confirm +5 s
    Note over CONF: (settle: HTTP, MQTT, SNTP bind sockets)
    CONF->>BOOT: boot_write_img_confirmed()
    Note over CONF: LOG_INF "firmware update confirmed"

    Note over BOOT,APP: If app crashes before confirm:<br/>next reset → MCUboot detects<br/>unconfirmed slot0 → SWAP_MOVE<br/>reverses → previous image restored

    EVT -->|callback| LISTENER
    LISTENER -->|lock| LOCK
    LOCK -->|copy| BUF
    BUF -->|unlock| LOCK

    TIMER -->|expiry| TX_PATH
    FORCE -->|command| TX_PATH

    WIRE -->|5-byte readings| LORA

    SNAP -->|calls| LORA
