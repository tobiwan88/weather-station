# REQ-FOTA — Firmware Over-The-Air Update Requirements

## Status
review

## Version
0.1

## Context
FOTA enables remote firmware updates via MCUboot bootloader with ED25519-signed images, dual-image slot management, and health-check-based image confirmation. Updates are delivered over HTTP (gateway) or LoRa (sensor nodes).

## Functional Requirements

### REQ-FOTA-001 — MCUboot Dual-Image Slots
The system shall use MCUboot with two image slots (slot 0: active, slot 1: update candidate), each 984 KB, with SWAP_MOVE mode for image replacement.

### REQ-FOTA-002 — ED25519 Image Signing
The system shall require all firmware images to be signed with ED25519. The gateway shall verify signatures before accepting uploaded images.

### REQ-FOTA-003 — HTTP FOTA Upload
The system shall accept firmware image uploads via `POST /api/fota/upload`, streaming directly to flash slot 1. The upload shall verify the image signature before writing.

### REQ-FOTA-004 — Image Confirmation with Health Checks
The system shall confirm the new image only after all registered health checks return `ok`. Health checks shall be registered via iterable section (`STRUCT_SECTION_ITERABLE(fota_health_check)`). If any check fails after `CONFIG_FOTA_CONFIRM_MAX_RETRIES`, the system shall let MCUboot roll back.

### REQ-FOTA-005 — Minimum Confirm Delay
The system shall wait a minimum of `CONFIG_FOTA_CONFIRM_MIN_DELAY_S` seconds before the first health check evaluation, allowing sockets and services to initialize.

### REQ-FOTA-006 — Reboot After Apply
The system shall reboot 2 seconds after marking slot 1 as pending via `POST /api/fota/apply`.

### REQ-FOTA-007 — FOTA Status API
The system shall report slot versions and confirmation state via `GET /api/fota/status`.

### REQ-FOTA-008 — Sensor Node FOTA over LoRa
The system shall trigger sensor-node firmware updates over LoRa via `POST /api/fota/sensor/<uid>/apply`, using the windowed chunk protocol (REQ-LORA-008).

### REQ-FOTA-009 — Development Key Management
The system shall support development keys generated by `scripts/gen-dev-key.sh`, stored in a `.gitignore`d `keys/` directory. Development keys shall never be committed to the repository.

### REQ-FOTA-010 — Manual Recovery Path
The system shall support firmware recovery via NXP ROM ISP bootloader or JTAG re-flash when MCUboot cannot boot a valid image.

### REQ-FOTA-011 — Flash Write Buffering
The system shall use a 4 KB flash write buffer for FOTA image writes to slot 1.

### REQ-FOTA-012 — Key Secrecy in CI
The system shall never expose signing key material in CI logs. Key injection shall use `printf '%s'` (not `echo`) with `+x` disabled.

## Dependencies
- REQ-HTTP-006: FOTA upload endpoint
- REQ-LORA-008: FOTA window protocol for sensor nodes
- REQ-LORA-014: External flash buffering for LoRa FOTA

## Constraints
- MCUboot size: 80 KB at 0x00000000
- Slot 0: 984 KB at 0x00014000
- Slot 1: 984 KB at 0x0010A000
- Total internal flash: 2 MB, 8 KB sectors, 8 KB-aligned boundaries
- External W25Q64 SPI flash: 8 MB for storage partition
- Image confirmation: 5 seconds settle time minimum
- Reboot delay after apply: 2 seconds
- MCUboot is hardware-only (`depends on BOOTLOADER_MCUBOOT`) — native_sim unaffected
